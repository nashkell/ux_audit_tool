# Evals

These measure whether the skill finds real problems, avoids false ones, and doesn't repeat itself. **Run them before releasing any version, and record the results in `CHANGELOG.md`.**

```bash
cd scripts && npm install && cd ..        # once
node evals/score.js --all
```

`--all` exits non-zero if any check fails or a metric drops below its floor in `bad-before/baseline.json`.

## What's here

| Path | What it checks |
|------|----------------|
| `carepath/` | The CarePath sample: `findings.csv`, `audit-meta.json`, and `expected-scores.json` (87.5% overall; 43 / 38.5 / 48.5 / 45; Top 5 ACC-001, UH-003, MOB-001, UH-001, ACC-002). Checks that scoring still reproduces those numbers and that `validate-findings.js` passes the clean sample. |
| `bad-before/expected.csv` | The answer key: 44 issues from the W3C [Before and After Demonstration](https://www.w3.org/WAI/demos/bad/) (BAD) "before" annotations for Home, News, Tickets, and Survey, plus the Template page's site-wide issues. |
| `bad-before/also-valid.csv` | Real issues the BAD annotations don't list (no page language, WCAG 2.2 target size, no landmarks). A finding matching one counts as precise but doesn't add to recall. |
| `bad-before/pages.json` | The four pages, for `capture-site.js`. |
| `bad-before/run-*.csv` | Scored runs. `run-automated.csv` is the automation-only baseline. |
| `bad-before/baseline.json` | Floors per run: recall and precision may not drop below them, duplicate rate may not rise above. |
| `score.js` | The scorer. |
| `automated-baseline.js` | Turns `capture-site.js` output into a findings CSV using automation alone. |

## Metrics

- **Recall:** expected issues found, out of all expected. Also reported for the A/AA items only, since some BAD notes cite only AAA or advisory guidance.
- **Precision:** reported findings that match an expected or also-valid issue. The BAD key isn't exhaustive, so this is a lower bound; unmatched findings are listed for a human to review.
- **Duplicate rate:** reported findings that only cover issues an earlier finding already covered. The consolidation rule should keep this near 0.

A finding covers an expected issue when it's on the right page (or it's Site-wide, or the issue is a template issue) and it's the same issue: it cites one of the issue's WCAG criteria and hits one of its keywords. A finding that cites no WCAG criterion needs two keyword hits. When grading a run by hand, add a `Matches` column with the expected IDs (e.g. `home-02; template-07`); it overrides automatic matching for that row.

## Scoring a full skill run

The automated baseline shows what axe and the capture checks find with no judgment. A real eval of the skill is a full audit of the four BAD pages:

1. In a fresh session **that hasn't seen `expected.csv` or the BAD annotated pages**, run the skill on `https://www.w3.org/WAI/demos/bad/before/home.html`, `news.html`, `tickets.html`, and `survey.html`, producing `findings.csv` as usual.
2. Save it as `bad-before/run-<version>.csv` (e.g. `run-v1.5.5.csv`).
3. `node evals/score.js evals/bad-before/expected.csv evals/bad-before/run-v1.5.5.csv --verbose`. Check the unmatched findings by hand; add any real ones to `also-valid.csv` with a reason.
4. Add a floor for the run to `baseline.json`, and record the numbers in the CHANGELOG.

To refresh the automated baseline (e.g. after a `capture-site.js` or axe-core change):

```bash
node scripts/capture-site.js https://www.w3.org --pages evals/bad-before/pages.json --output /tmp/bad-capture
node evals/automated-baseline.js /tmp/bad-capture evals/bad-before/run-automated.csv
node evals/score.js evals/bad-before/expected.csv evals/bad-before/run-automated.csv
```

## Adding a real client page later

There's deliberately no real-site eval yet. To add one:
1. Create `evals/<site-name>/` with `pages.json` (the URLs) and an `expected.csv` in the same format as `bad-before/expected.csv`, **hand-verified** by a person against the live pages (not generated by the skill).
2. Record the date the expected list was verified; live sites change, so re-verify before trusting a drop in recall.
3. Get the client's agreement before committing anything from their site.
